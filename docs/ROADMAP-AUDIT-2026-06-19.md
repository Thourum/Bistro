### Phase 2.1/2.2 — patchset timeline & since-last-review

#### 🔴 Patchsets cannot be reconstructed by polling: intermediate force-pushes are invisible

- **Severity / kind:** critical · infeasible-as-specified
- **Location:** `docs/ROADMAP.md section 2.1`
- **Assumption:** Each push to a PR is recorded as a patchset with a sequential number, its head SHA, and its timestamp. Patchsets persist even after rebase.
- **Reality:** The sync engine calls PullRequests.List (go/internal/provider/github/pull_requests.go:23) and reads only ghPR.GetHead().GetSHA() (line 65). A ~5-min poll sees only the current head SHA. Any force-push that happened and was superseded by another push between two polls is permanently invisible — there is no before/after SHA recorded, no push timestamp, and no push count. If an author pushes P2 and P3 within the same 5-min window, Bistro will record only P3 (or whichever is current at poll time), silently skipping P2.
- **Evidence:** go/internal/provider/github/pull_requests.go:23 (PullRequests.List), line 65 (HeadSHA = GetHead().GetSHA()); go/internal/provider/interface.go (no GetTimeline/ListCommits/GetPushEvents method); go-github v84 issues_timeline.go reviewed — Timeline struct event list does not include head_ref_force_pushed and has no BeforeCommit/AfterCommit fields; no ListIssueTimeline call anywhere in go/internal/
- **Recommendation:** To reliably capture every push, call PullRequests.ListCommits (exists in go-github v84 at pulls.go:401) on every sync cycle and record a snapshot whenever head SHA changes. Alternatively call IssuesService.ListIssueTimeline and filter for 'committed' events, but note the Timeline struct carries no force-push before/after SHAs. The only API that exposes before/after SHAs for force-pushes is the GitHub Push webhook — but Bistro is local-first with no server, so webhooks require a different architecture. Accept that polling-based patchsets will miss intermediate pushes and document that limitation explicitly, or add a per-PR fast-sync (roadmap item 1.4, not started) that polls the open PR every 30s.
- **Verifier note:** All key claims independently verified: 1. Polling reads only current head SHA: go/internal/provider/github/pull_requests.go line 65 — normalizePR sets HeadSHA = ghPR.GetHead().GetSHA() from PullRequests.List. No ListCommits call exists anywhere in go/internal/. 2. Provider interface has no timeline/commit-history method: go/internal/provider/interface.go — interface is ListPRs, GetPR, GetComments, ListReviews, GetCIStatus, Approve, RequestChanges, PostComment, GetUsername, ListUserRepos. No GetTimeline, ListCommits, or GetPushEvents. 3. Timeline struct in go-github v84 confirmed to lack head_ref_force_pushed and BeforeCommit/AfterCommit fields: issues_timeline.go:18–163 — the enumerated event types do not include head_ref_force_pushed, and the struct has no before/after SHA fields. 4. PullRequestsService.ListCommits does exist in go-github v84 (github-iterators.go:4913 shows ListCommitsIter wrapping ListCommits) — so the recommendation's mitigation option is feasible. 5. The roadmap (ROADMAP.md:160,162) explicitly says patchsets are "computed from local git history" via go-git clone — but a local fetch also only captures the state at fetch time. If P2 is force-pushed away before Bistro fetches, the local clone never records P2, and no pushed_at timestamp is available. 6. No patchsets migration exists (migrations 000–010 listed; 011 adds comment classification only) — the table doesn't exist yet, confirming this is a future design gap, not a current implementation bug. The finding correctly identifies that polling (whether via GitHub API or local git fetch) at ~5min intervals cannot reconstruct intermediate force-pushes. The pushed_at field in the proposed schema has no reliable source. The finding's library facts (Timeline struct, ListCommits availability) are accurate. The severity label (critical) may be strong since Phase 2 is not yet implemented, but the architectural gap is real and confirmed.

#### 🔴 go-git v5.17.2 has no range-diff implementation; the 'git range-diff semantics' promise is unbuildable with the current library

- **Severity / kind:** critical · wrong-assumption
- **Location:** `docs/ROADMAP.md sections 2.1 and 2.2`
- **Assumption:** Diffing arbitrary patchset pairs uses 'git range-diff' semantics, not raw commit diff (so no-op rebases produce empty diffs). 2.2 toggle renders 'git range-diff last_reviewed_sha..head_sha' against the prior base/head.
- **Reality:** grep -r 'range.diff|RangeDiff|range_diff' against the go-git v5.17.2 module cache (/Users/samuelasvanyi/go/pkg/mod/github.com/go-git/go-git/v5@v5.17.2/) returns zero matches for any range-diff API. The only diff surface is Tree.Patch(otherTree) (a plain tree-to-tree unified diff), which is what Bistro already uses in go/internal/git/diff.go:68. Range-diff is a fundamentally different algorithm: it matches commits from two ranges by their patch content and produces a meta-diff of the diffs. There is no way to compose Tree.Patch calls to reproduce it.
- **Evidence:** grep result: 'NOT FOUND in go-git module cache' for range-diff/RangeDiff patterns; go/internal/git/diff.go:68 uses baseTree.Patch(headTree); go/go.mod line 6: github.com/go-git/go-git/v5 v5.17.2; Bistro has no os/exec calls in any production Go file (grep confirmed)
- **Recommendation:** Three options, each with a real cost: (1) Shell out to system 'git range-diff' via os/exec — breaks the local-first/no-system-git assumption and adds a hard runtime dependency on a system git >= 2.19. (2) Implement range-diff by hand in Go: compute patch fingerprints for both commit ranges, match pairs by content similarity (Myers diff on the diffs), and render the meta-diff. This is ~500–1000 lines of non-trivial algorithm code with no library support. (3) Change the spec: instead of true range-diff, compute a merge-base diff (diff of diff of base→P_old vs base→P_new) which approximates the intent for simple rebases but breaks for squashes. The roadmap must explicitly pick one option and assign the cost before Phase 2 starts.
- **Verifier note:** Three independent checks all corroborate the finding. 1. go-git v5.17.2 module cache grep for 'range.diff|RangeDiff|range_diff' returns zero matches for any range-diff API — only incidental loop-variable `range` hits in unrelated files. The object package contains only difftree.go and patch.go; neither implements range-diff. Verified at /Users/samuelasvanyi/go/pkg/mod/github.com/go-git/go-git/v5@v5.17.2/. 2. ROADMAP.md lines 177 and 203 (§2.1 and §2.2) explicitly state: "Diffing arbitrary patchset pairs uses `git range-diff` semantics, not raw commit diff (so no-op rebases produce empty diffs)" and "'Since last review' toggle renders `git range-diff last_reviewed_sha..head_sha` against the prior base/head." These are unambiguous promises of range-diff behaviour. 3. go/internal/git/diff.go:68 implements only baseTree.Patch(headTree) — a plain tree-to-tree unified diff. No os/exec calls exist in any production Go file under go/internal/, so there is no existing workaround via system git either. The roadmap promises range-diff semantics, go-git v5.17.2 has no such API, and the current implementation does not approximate it. The finding is correct on every factual claim.

#### 🟠 Patchset schema has a type mismatch: pr_id INTEGER vs prs.id TEXT

- **Severity / kind:** high · data-model-bug
- **Location:** `docs/ROADMAP.md section 2.1 (proposed schema)`
- **Assumption:** CREATE TABLE patchsets (pr_id INTEGER NOT NULL, ..., PRIMARY KEY (pr_id, number))
- **Reality:** prs.id is TEXT PRIMARY KEY (migration 001_init.sql:5), with values like 'github:owner/repo:123'. Declaring patchsets.pr_id as INTEGER means the foreign key reference to prs(id) would be a type mismatch. SQLite's weak typing will silently accept the insert but the FK constraint will never match a TEXT primary key via an INTEGER foreign key column, so ON DELETE CASCADE will not fire and JOIN queries will return no rows.
- **Evidence:** go/internal/store/migrations/001_init.sql:5 (id TEXT PRIMARY KEY); roadmap section 2.1 schema block (pr_id INTEGER NOT NULL); also confirmed by KEY VERIFIED FACTS: 'prs.id is TEXT (e.g. "github:owner/repo#1")'
- **Recommendation:** Change the proposed schema to: patchsets(pr_id TEXT NOT NULL, FOREIGN KEY(pr_id) REFERENCES prs(id) ON DELETE CASCADE). Mirror the pattern already used correctly in migrations 007_add_pr_diffs.sql:6 (pr_id TEXT NOT NULL).
- **Verifier note:** Three independent checks confirm the finding exactly as described: 1. go/internal/store/migrations/001_init.sql:5 — prs.id is declared `id TEXT PRIMARY KEY`. 2. docs/ROADMAP.md:183 — the proposed patchsets schema declares `pr_id INTEGER NOT NULL`, a type mismatch against the TEXT primary key. 3. go/internal/store/migrations/007_add_pr_diffs.sql:6 — the correct pattern already used in the codebase is `pr_id TEXT NOT NULL, FOREIGN KEY(pr_id) REFERENCES prs(id) ON DELETE CASCADE`. The recommendation in the finding is also correct: the proposed schema should use `pr_id TEXT NOT NULL` to match the pattern in migrations 007 (and 001 for comments). The mismatch in the roadmap schema is a copy error that would cause FK cascade and JOIN failures at runtime.

#### 🟡 Bistro has no system git dependency — range-diff via shell-out would break the local-first constraint

- **Severity / kind:** medium · sequencing-hazard
- **Location:** `go/internal/git/ (entire package), docs/ROADMAP.md Phase 0 architecture`
- **Assumption:** go-git for clone + unified diffs — foundation for every 'since I last reviewed' feature later (Phase 0 table, status: done).
- **Reality:** The git package is pure go-git with zero os/exec calls (confirmed by grep). The AGENTS.md architecture note says 'go-git v5' without qualification. If range-diff is implemented via os/exec shell-out to system git, this introduces: (1) a hard runtime dependency on system git >= 2.19 (range-diff was added in git 2.19), (2) an unavoidable breakage on macOS where Xcode Command Line Tools ships git 2.x but not always a recent enough version, (3) cross-platform path quoting issues. None of this is acknowledged in the roadmap.
- **Evidence:** grep -rn 'os/exec|exec.Command' go/internal/ --include='*.go' (excluding _test.go) returned zero matches; go/go.mod line 6 confirms go-git v5.17.2 as the only git library; AGENTS.md 'go-git for clone + unified diffs'
- **Recommendation:** The roadmap must explicitly decide before Phase 2 begins: pure-Go range-diff implementation (no system dependency, ~500–1000 lines) vs. shell-out (system git dependency, breaks local-first claim). A third option — define 'range-diff semantics' as merge-base tree diff rather than true patch-matching — is achievable with current go-git but produces different results for squash rebases and should not be called 'range-diff'.
- **Verifier note:** Three independent checks support the finding: 1. **No os/exec in the codebase**: `grep -rn 'os/exec|exec.Command' go/internal/ --include='*.go'` (excluding _test.go) returns zero matches. The roadmap never states whether this will be pure-Go, shell-out, or an approximation. The implementation strategy is an open decision. 3. **go-git v5.17.2 has no range-diff API**: The current diff.go implements only tree-to-tree unified diff. True `git range-diff` requires commit-pair matching via patch similarity scoring — an algorithm go-git does not expose. Phase 2 hasn't been built yet, so no implementation exists to evaluate; but the gap between "what go-git provides" and "what the roadmap requires" is real and unacknowledged. The finding is slightly conditional in framing ("if range-diff is implemented via shell-out") rather than documenting an existing defect — but its core claim is accurate: the roadmap is silent on implementation strategy for a semantically complex feature that go-git cannot deliver natively, and a shell-out would introduce a hard system-git version dependency (≥2.19) that contradicts the local-first, zero-system-dependency architecture. ### Phase 2.3/2.4 — comment anchoring & unresolved threads

#### 🔴 Only issue-level comments are fetched — review/diff comments are entirely missing

- **Severity / kind:** critical · wrong-assumption
- **Location:** `go/internal/provider/github/comments.go:14-22`
- **Assumption:** Phase 2.3 and 2.4 assume comments in SQLite represent the full set of GitHub review threads, including inline diff comments that need anchoring.
- **Reality:** The provider calls `Issues.ListComments` (issue-level general comments), not `PullRequests.ListComments` (diff/review comments). The normalizeComment function (line 39-48) maps to provider.Comment with LineNo always 0 and FilePath always empty, because IssueComment has no path or line fields. All inline diff comments — the entire input for anchoring and thread resolution — are never fetched, never stored, and invisible to the engine.
- **Evidence:** go/internal/provider/github/comments.go:14 uses `ghlib.IssueListCommentsOptions` and `c.gh.Issues.ListComments`. The `IssueComment` type in go-github v84 has no `Path`, `Line`, `CommitID`, or `Position` fields. go-github v84 `PullRequestComment` struct at ~/go/pkg/mod/github.com/google/go-github/v84@v84.0.0/github/pulls_comments.go:15-51 has all of those.
- **Recommendation:** Before any Phase 2.3/2.4 work, add a `PullRequests.ListComments` call to the fetcher and a second normalizer that maps `PullRequestComment` fields (CommitID, OriginalCommitID, Path, Line, OriginalLine, Side, Position, OriginalPosition) into the store. The two comment types need to co-exist in the schema as distinct rows with distinct ID namespaces.
- **Verifier note:** Independently verified all three pillars of the finding: 1. go/internal/provider/github/comments.go:14-22 — uses ghlib.IssueListCommentsOptions and c.gh.Issues.ListComments exclusively. normalizeComment (lines 39-48) constructs a provider.Comment with only ID, PRID, Author, Body, CreatedAt, UpdatedAt — LineNo and FilePath are never set, so they are always zero/empty. 2. go-github v84 library fact ($(go env GOMODCACHE)/github.com/google/go-github/v84@v84.0.0/github/pulls_comments.go) — PullRequestComment has Path, Line, OriginalLine, StartLine, OriginalStartLine, Side, StartSide, CommitID, OriginalCommitID, Position, OriginalPosition. The full set of GitHub PR review/diff comments (fetched via PullRequests.ListComments, type PullRequestComment) is never fetched, never normalized, and never stored. Phase 2.3/2.4 anchoring would work on a structurally incomplete comment set.
