# NIH / Custom Implementation Audit

Date: 2026-07-12

This is a survey only. No code was modified. The recommendations below are intentionally conservative: for a local-first desktop app, small tested custom code is often better than adding dependencies. The bar for `REPLACE` is that the code tracks a moving target, implements tricky parsing/lifecycle behavior, or duplicates an already-installed dependency.

## Per-item detail

### 1. Unified diff parsing in the renderer

- **Location:** `electron/src/renderer/utils/diff-parser.ts:23`
- **What is custom:** The renderer splits raw git diff text on `diff --git`, extracts quoted and unquoted file names, parses hunk headers, and assigns old/new line numbers by hand. This is a real parser for an externally-defined format with many edge cases: renames, binary files, quoted paths, missing newline markers, mode-only changes, and unusual hunk ranges.
- **Candidate:** First check whether already-installed `@pierre/diffs` exposes parsing primitives that can replace this. If not, the maintained `diff` npm package exposes `parsePatch` and is widely used.
- **Tradeoff:** A parser library buys correctness on edge cases and fewer local tests. It costs a dependency or a deeper coupling to `@pierre/diffs`, plus migration from the current `DiffSection` shape.
- **Recommendation:** `REPLACE`. Diff parsing is not worth owning if a maintained parser can produce the data needed by the UI.

### 2. LLM pricing table

- **Location:** `go/internal/classify/llm/tier.go:349`
- **What is custom:** Provider/model cost estimation uses hard-coded pricing data. Pricing changes independently of Bistro releases and often differs by model, prompt tokens, output tokens, cache reads, and cache writes.
- **Candidate:** Use OpenRouter model pricing metadata or LiteLLM's maintained `model_prices_and_context_window.json` as the pricing source, with local fallback values for offline use.
- **Tradeoff:** Maintained pricing buys freshness and model specificity. It costs an extra data fetch/cache path or a vendored JSON update process.
- **Recommendation:** `REPLACE`. Pricing is a moving external target; hard-coding it guarantees drift.

### 3. Electron settings persistence

- **Location:** `electron/src/main/settings.ts:39`
- **What is custom:** `SettingsService` reads and writes JSON under `userData`, normalizes partial settings, watches the file, suppresses self-write reloads, broadcasts changes, and supports renderer migration/fallback behavior.
- **Candidate:** `electron-store` or `conf` for storage/defaults/migrations/watch. The repo already has `zod`, which can validate the settings file at runtime without adding a schema library.
- **Tradeoff:** A config-store library buys well-tested persistence, migrations, defaults, and watch behavior. It costs another dependency and may require adapting current settings broadcast semantics.
- **Recommendation:** `BORDERLINE`. Replace if settings keep growing or file-watch bugs appear; otherwise keep custom and add `zod` validation first.

### 4. Go sync-engine process lifecycle

- **Location:** `electron/src/main/go-spawn.ts:92`
- **What is custom:** The main process uses raw `child_process.spawn`, manual stdout/stderr line buffering, ready-signal parsing, timeout handling, port probing, restart limits, and shutdown logic.
- **Candidate:** `execa` for subprocess lifecycle, `wait-on` or `tcp-port-used` for readiness checks, and `tree-kill` if cross-platform process-tree cleanup is needed.
- **Tradeoff:** Libraries buy cancellation, stream handling, Windows behavior, and readiness edge cases. They cost dependency surface and still require Bistro-specific ready JSON parsing.
- **Recommendation:** `BORDERLINE`. This is important enough to consider replacing, but current behavior is app-specific enough that a partial adoption may be best.

### 5. Store-layer SQL boilerplate

- **Location:** `go/internal/store/diff_store.go:30` and sibling store files
- **What is custom:** Store packages use raw `database/sql` queries and manual row scanning for diffs, review threads, current user, dismissals, viewed files, patchsets, sync cursors, and action queues.
- **Candidate:** `sqlc` for generated typed query methods, or `sqlx` for lighter struct scanning.
- **Tradeoff:** `sqlc` buys compile-time query checking and typed row structs with no runtime dependency. It costs a generation step, query organization, and migration of existing stores.
- **Recommendation:** `REPLACE`. This is the biggest broad maintenance win, especially because SQLite schema changes are ongoing.

### 6. Migration runner

- **Location:** `go/internal/store/migration_runner.go:26`
- **What is custom:** The runner embeds SQL files, parses version/description from filenames, creates `schema_migrations`, tracks applied versions, and runs pending migrations in transactions.
- **Candidate:** `pressly/goose/v3` or `golang-migrate/migrate/v4` with SQLite and embedded migrations.
- **Tradeoff:** A migration library buys battle-tested version tracking and fewer bespoke migration edge cases. It costs a dependency and potential adaptation to the current embedded migration layout.
- **Recommendation:** `BORDERLINE`. Worth replacing if migrations get more complex; acceptable to keep if the current runner is well-covered and intentionally minimal.

### 7. Offline action queue

- **Location:** `go/internal/store/action_queue.go:42`
- **What is custom:** Bistro has a SQLite-backed queue for offline review actions, retry counts, action states, account scoping, processing reset, completion/failure, and deletion helpers.
- **Candidate:** A SQLite-focused job queue library if one meets the local-first requirement. `asynq` is maintained but Redis-backed, so it conflicts with Bistro's local-only architecture.
- **Tradeoff:** A queue library buys retry semantics and worker lifecycle. It costs heavy infrastructure assumptions or weaker control over Bistro's action schema.
- **Recommendation:** `KEEP CUSTOM`. The queue is core local-first product behavior, not generic background jobs.

### 8. WebSocket hub

- **Location:** `go/internal/ws/server.go:17`
- **What is custom:** The server wraps `gorilla/websocket` with localhost-origin checks, connection tracking, per-connection write locks, broadcast fan-out, accept loop, request/response writes, and shutdown.
- **Candidate:** `centrifugal/centrifuge` for maintained channels, pubsub, client lifecycle, and broadcasting.
- **Tradeoff:** A hub library buys lifecycle correctness and richer realtime primitives. It costs substantial dependency and conceptual weight for a localhost-only desktop IPC channel.
- **Recommendation:** `BORDERLINE`. Keep for now unless connection lifecycle bugs or multi-channel realtime semantics grow.

### 9. Electron IPC routing and validation

- **Location:** `electron/src/main/ipc.ts:23`
- **What is custom:** IPC uses manual `ipcMain.handle` registrations, preload wrappers, channel typing, channel allowlists, and TypeScript request/response types. Runtime validation at this process boundary is limited.
- **Candidate:** `electron-trpc` for typed IPC, or the already-installed `zod` for request schemas without changing the transport.
- **Tradeoff:** A framework buys end-to-end typing and validation patterns. It costs migration churn and another abstraction over Electron IPC.
- **Recommendation:** `BORDERLINE`. Prefer adding `zod` validation to current handlers before adopting a full IPC framework.

### 10. GitHub PR anchor resolution

- **Location:** `go/internal/git/anchor.go:64`
- **What is custom:** Anchor resolution maps GitHub review comment positions across patchsets and diffs, including base/current patchset handling and outdated comment candidates.
- **Candidate:** Continue using existing `go-git` and `sergi/go-diff` primitives where they reduce local parsing, but no maintained library clearly owns GitHub PR review-comment anchoring end to end.
- **Tradeoff:** More library use could reduce low-level diff math. It would not replace the product-specific semantics and could obscure already subtle behavior.
- **Recommendation:** `KEEP CUSTOM`. This is domain logic, not NIH, as long as tests cover GitHub edge cases.

### 11. Telemetry pipeline

- **Location:** `electron/src/main/telemetry.ts:155`
- **What is custom:** Telemetry handles event typing/sanitization, anonymous install ID persistence, JSONL disk storage, endpoint resolution, and upload plumbing. The repo already includes `@sentry/electron`, which overlaps with event/error telemetry infrastructure.
- **Candidate:** Reuse `@sentry/electron` for consented custom events, or use PostHog/OpenTelemetry if product analytics requirements outgrow Sentry.
- **Tradeoff:** A maintained telemetry SDK buys batching, retry, privacy controls, and transport edge cases. It costs vendor coupling and may not match the custom offline JSONL endpoint format.
- **Recommendation:** `BORDERLINE`. Keep custom only if Bistro needs its own endpoint/offline format; otherwise consolidate with Sentry.

### 12. Markdown-ish dedup normalization

- **Location:** `go/internal/classify/dedup.go:101`
- **What is custom:** Dedup strips fenced code blocks by scanning for triple backticks, lowercases, removes punctuation, and rejoins fields. It misses full Markdown edge cases like tildes, indented blocks, nested/unclosed fences, and some language attributes.
- **Candidate:** `goldmark` AST parsing to remove code blocks and normalize Markdown text.
- **Tradeoff:** `goldmark` buys correct Markdown parsing. It costs a sizable dependency for a fuzzy heuristic where perfect parsing may not matter.
- **Recommendation:** `KEEP CUSTOM`. Revisit only if dedup false positives/negatives are traced to Markdown parsing.

### 13. Trigram Jaccard and union-find dedup

- **Location:** `go/internal/classify/dedup.go:135`
- **What is custom:** Near-duplicate detection builds trigram sets, computes Jaccard similarity, thresholds candidate pairs, and uses a local union-find for connected components.
- **Candidate:** `adrg/strutil/metrics` for similarity plus `gonum/graph` for connected components.
- **Tradeoff:** Libraries buy tested algorithms. They cost dependencies, especially `gonum`, for code that is small and easy to test locally.
- **Recommendation:** `KEEP CUSTOM`. This is the right kind of small custom code unless accuracy or performance becomes a measured problem.

### 14. Go WebSocket handler request validation

- **Location:** `go/internal/server/handler/pr.go:76` and sibling handlers
- **What is custom:** Handlers repeatedly decode JSON and manually validate required fields, ranges, and enum-like values across PR, diff, comments, dismissals, sync, settings, and thread messages.
- **Candidate:** `go-playground/validator/v10` with struct tags, or generated JSON Schema validation if the WebSocket protocol is formalized.
- **Tradeoff:** A validator buys consistency at trust boundaries. It costs another dependency and can hide validation logic in tags.
- **Recommendation:** `BORDERLINE`. Add a validator if validation errors keep diverging; otherwise keep explicit checks near handlers.

### 15. Dismissal undo stack

- **Location:** `electron/src/renderer/utils/dismissals.ts:59`
- **What is custom:** Dismissal undo is a small immutable stack for batched comment IDs, with push/pop helpers and report formatting.
- **Candidate:** `use-undo`, `use-undoable`, or another React history hook.
- **Tradeoff:** A library buys a generic undo model. It costs adapting domain-specific WebSocket payloads to a generic state history abstraction.
- **Recommendation:** `KEEP CUSTOM`. This is small, readable, and domain-shaped.

### 16. Renderer localStorage sync

- **Location:** `electron/src/renderer/hooks/useStoreSync.ts:14`
- **What is custom:** The hook hydrates UI state from `localStorage`, serializes selected fields, subscribes to store changes, and logs JSON parse/storage errors.
- **Candidate:** `usehooks-ts` or `@uidotdev/usehooks` localStorage hooks.
- **Tradeoff:** A hook library buys less boilerplate. It costs a dependency for about 40 lines of straightforward platform code.
- **Recommendation:** `KEEP CUSTOM`. This is too small to justify a new dependency.

### 17. Visible PR filtering/search/sort

- **Location:** `electron/src/renderer/hooks/useVisiblePRs.ts:33`
- **What is custom:** The visible PR hook combines filter state, repository filter, substring query matching, and date/status sorting.
- **Candidate:** `match-sorter` or `@tanstack/match-sorter-utils` for maintained ranked/fuzzy filtering.
- **Tradeoff:** A matching library buys fuzzy ranking and predictable scoring. It costs dependency weight and product behavior changes.
- **Recommendation:** `KEEP CUSTOM`. Add a matcher only when product requirements call for fuzzy search.

## Findings intentionally not ranked

- **LLM HTTP client replacement:** Earlier inspection found a hand-written OpenAI/Anthropic HTTP client candidate. Current repo state already imports `github.com/openai/openai-go` and `github.com/anthropics/anthropic-sdk-go` in `go/internal/classify/llm/client.go`, so this appears already resolved or in progress.
- **Generic test helpers/fakes:** The audit found many mocks/fakes, but most are test-local and domain-specific. Adding `testify`, `go-cmp`, or a mock generator only for these would not clearly reduce complexity.
- **Small stdlib wrappers:** Several small `contains`/filter/key helpers exist, but none cleared the bar for a maintained-library replacement. Prefer Go stdlib `slices`/`maps` opportunistically during normal edits rather than broad churn.
